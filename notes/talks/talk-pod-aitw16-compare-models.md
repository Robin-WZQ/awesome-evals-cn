# 笔记——“#16 跨模型评估提示词”
**讲者/嘉宾：** AI That Works · **出处：** AI That Works · **类型：** 播客 · **链接：** https://www.youtube.com/watch?v=OawyQOrlubM

## 摘要（3—6 句：核心主张及其对智能体评测的意义）
Vaibhav（Vibhav/“Vibbob”，BAML）和 Dex（HumanLayer、12-Factor Agents）讨论了一个反复出现的实践问题：新模型发布后，应该如何决定是否替换现有模型？他们的答案是：对于大多数已经运行的系统，**不要**更换——已知模型是“熟悉的敌人”，而评估变更的成本很高。由于几乎没人拥有自动化评测，最后只能做天然缓慢的“凭感觉评测”。本期大部分内容是在屏幕共享下现场用 Python、BAML 和 Streamlit 搭建一个定制的跨模型“凭感觉评测”工具：把模型输出以 JSON 写入磁盘，以异步方式运行所有模型与所有测试用例的笛卡尔积，再用并排界面直接阅读生成的邮件。核心论点是，“准确率”只是一个定义不清的质量替代指标，其含义完全取决于具体业务场景，因此评测工具必须定制；真正困难、缓慢的工作不是 AI 本身，而是搭建能让个人或团队快速判断“什么才算好”的基础设施和界面。对智能体评测而言，本期具体展示了“90% 的工作是数据管道”的现实、为何此时使用 LLM 裁判往往为时过早，以及如何把临时的模型比较转化为可复用的内部工具。

## 要点（6—14 条实质性内容）
- **默认不要替换。** 系统运行正常时就不要更新；新模型是“未知的敌人”，而且“真正确认模型能否工作所需的投入并不值得，尤其是在系统没有坏掉时”。如今多数人会先“让别人凭感觉检查”。
- **阶跃式提升是例外。** 有些现实升级足以推翻上述默认原则：GPT-4 → GPT-4o（Dex 的 SQL 审计日志摘要流水线，仅因速度和用户体验提升 2—4 倍而选择它，尽管它“稍微笨一点”；该流水线会并行运行大量“对摘要再摘要”的提示词）；GPT-4o-mini 带来数量级的延迟下降；DeepSeek 的开源权重即使质量稍低，也开启了新的使用场景。
- **私人基准确实存在。** 人们会保存一组秘密提示词作为个人基准。Simon Willison 的“感觉基准”是让 Nova、Llama 3.3、DeepSeek 从零生成“一只骑自行车的鹈鹕”的 SVG；这明确只是感觉测试，不是技术基准。
- **生产评测前先建立两阶段直觉（Vaibhav 的方法）：**（1）有意“关闭”自己对模型能力边界的先验，用一个**更短、更含糊**的提示词逼近其极限，运行 20—30 次，凭感觉检查它能否解决更难的问题或更擅长特定领域；（2）只有通过后，才在真实生产任务上评测。
- **在完整执行框架中评测模型，而非只看输入输出。** 不应只测试“输入文本和提示词后输出什么”，还要退一步判断模型在“合适的执行框架中是否足够聪明”。例如，Claude Code 能否通过多轮工具调用一次完成 LinkedIn 帖子（Dex 的“social”提示词会下载白板图片并撰写帖子）。应评估架构，而不只是模型。
- **替换提示词的成本约等于开发一个新功能，但验证更慢。** 如今写功能很快（智能体会写代码），但评估 AI 流水线“总会非常慢，因为多数人没有自动化评测”，于是只能退回缓慢的感觉评测——这才是真正的瓶颈。
- **BDD/Gherkin 不适用于 AI。** Ben Stein 对 AI 产品经理的观察是：能力具有涌现性，因此无法预先写好“给定/当/那么”。你要先把新模型放进产品，发现它如今能做什么，**然后**把这一能力固化为规格并编写评测。
- **“准确率”是定义不清的质量替代指标，**在不同语境中含义不同：事实数据上的幻觉率、能否产出可运行代码，或语气是否合适。能否容忍 20% 的失败（“能想象 REST API 有 20% 的请求失败吗？”）取决于是否有人类在环修正那 20% 的错误（如凭感觉编程），抑或系统完全自动化且出错会造成伤害（如复现法规文本）。
- **从业务场景反向定义准确性。** 以邮件为例：当人类把输出粘贴进 Loops 时，“hello first name”无关紧要；一旦流程完全自动化，把 `hello first name` 生成为可替换变量便成为硬性正确性约束——“我的准确性约束和定义已经发生根本变化”。少一条要点可以接受，语气糟糕则算失败。
- **评测工具的具体做法：**先用一个测试用例，放入 4o-mini、Sonnet 4 和 Opus 4 验证直觉；将测试数据以 JSON 存盘；按名称加载测试；对模型 × 测试做嵌套循环；以**异步、最大并行度**运行；刻意**不用 pytest**，因为评测是探索性的，“与 Jupyter notebook 的相似程度远高于单元测试框架”；使用 BAML 动态客户端注册表在运行时替换模型名。
- **容错运行器模式。** 每个单元都包在“不允许失败”的 `try/except` 中并自行保存到磁盘，因为扩展到 100—500 次运行后一定会遇到模型服务中断；设计时就要支持局部失败和重试。
- **JSON 无法用于判断；必须构建界面。** “JSON 文件就是垃圾。”一个实际却常被低估的事实是，基础设施与界面的工作量“惊人地大”，呼应机器学习时代的规律：“90% 的工作是把数据整理成正确形态。”他们用 Streamlit 构建了带并排 A/B 模型下拉框的应用；展示形式必须匹配产物（邮件渲染成 Markdown，坐标任务在图像上画框）——每个评测界面都“需要定制且独一无二”。
- **现场加入的低成本、高信号运行时/评测防护：**用正则高亮长破折号和其他“LLM 痕迹”（长破折号、`comprehensive`、`undoubtedly`——标记 AI 腔文案；人们会自动过滤带长破折号的邮件）；检测占位符和 `[方括号]`；验证链接有效性（请求每个链接并期待状态码 200）。“不需要做到完美……够用就行。”
- **此时使用 LLM 裁判为时过早。** “我甚至不知道要让它依据什么来评判。”如果没有清晰定义优秀邮件，裁判就帮不上忙；即使使用，还得单独评估裁判提示词，形成“巨大的元问题”。
- **护城河是品味，以及关于何为优秀的数据。** Amplify Partners 的 Sarah/Zara 从 100 位 AI 创始人那里得到的结论是：评测框架像其他测试系统一样容易搭建，价值在于**生成**好与坏的数据。这呼应了“Brian”那一期：嘉宾愿意共享代码和提示词，却不愿展示评测集。
- **定制与通用。** 定制方案没有问题，实施简单且灵活性完整（类似 shadcn：先搭骨架再定制）；但场景若足够通用，现成工具（如边界框标注器）更优——而且“如果你为一个极其通用的场景构建评测，那你大概已经没戏了，因为这玩意已经存在五年了。”
- **整个过程的速度：**不到一小时就从零完成完整测试套件、多模型查看与可用界面（其间 Cursor 还意外删除了全部代码）。

## 独特增量（相较于规范书面资料，本演讲提供的非显然价值）
这是一次跨模型比较框架的**现场构建**，因此揭示了常规评测文章略过的那些并不光鲜的决策：为什么选择**异步而非 pytest**（评测具有探索性，形态更像 notebook，并需要容忍局部失败——每个单元都包在不会中止全局的 `try/except` 中）；为什么 **JSON 输出毫无助益**，真正的评测其实是并排渲染界面；以及管道工作的比重有多大（模型名中的斜杠转义、JSON 模式序列化、目录结构）。它还给出了一个清晰可复用的框架：“准确率”是随语境变化的质量替代指标；一旦人类退出流程，其定义就会瞬间改变（`hello first name` → Loops 自动化的例子）。本期还提出具体的**多维评测矩阵**：同时按测试用例 × 模型 × 提示词版本 × 来源期数建立索引，不可能有厂商能卖给你“完美界面”。它提供了实用的廉价防护措施（正则检测 LLM 痕迹/长破折号、占位符检测、链接状态码 200 检查），并将其定位为“够用即可”；同时坦率指出，在目标尚无法定义时，LLM 裁判还为时过早。最后的元观点——真正的护城河是品味，以及“什么才算好”的硬编码记录，而不是评测框架——把评测重新定义为品味的捕获，而非评分基础设施。另有一个坦诚的实战插曲：Cursor 在演示中悄悄删除了所有代码，由此引出了 HumanLayer“盯着代码，别亲自写代码”的规格审查工作流预告。
